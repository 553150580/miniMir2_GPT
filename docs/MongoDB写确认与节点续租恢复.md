# MongoDB 写确认与节点续租恢复

## 2026-11-20 试玩故障

21:39:42，游戏节点的续租请求触发两秒超时。用相同 TCP 源端口与 MongoDB 慢操作日志配对，服务端记录该续租耗时 1999 毫秒，其中 1998 毫秒在等待写确认。相近时段另外两次续租和一次业务提交也记录写确认延迟。原 supervisor 在任何一个节点因续租失败退出后终止其余节点，导致登录接口与游戏连接同时中断。

本机开发数据库是单成员 MongoDB 8.0.34 副本集。多数写确认仍需等待本地日志落盘。MongoDB 的 21:39:41 至 21:39:43 三次历史采样中，有一个文件系统同步调用未完成，NVMe 的磁盘队列从 1 增到 4，同期磁盘读写完成量和 MongoDB 的 durable/lastCommitted 水位都未推进。21:39:44 日志同步与磁盘 I/O 恢复，水位追平。这把故障近因定位为本机存储 I/O 短时停顿。事发前 36 秒同一 NVMe 的上游 PCIe 端口有已更正错误，缺少与事故同一时刻的磁盘复位或文件系统错误记录，尚不能归因到具体硬件或驱动。参见 [MongoDB 8.0 写确认语义](https://www.mongodb.com/docs/v8.0/reference/write-concern/)。

21:44:06 恢复试玩后，账号、游戏和 GM 健康检查通过。网页代理能够把实际登录协议请求转给账号服务，并正常建立游戏 WebSocket。数据库一直使用同一专属副本集进程。

## 恢复边界

节点续租保持独立控制连接池和持久写确认。网络超时或明确可重试的写确认失败会在仍已确认的租约窗口内有限重试。窗口以最近一次完整成功续租的请求起点保守估计，15 秒数据库租期预留 3 秒安全隔离时间。未确认的部分更新不延长本地窗口。所有权丢失或越过截止时隔离本节点并停止现有请求。MongoDB 的 owner、epoch 及数据库时间条件继续负责判定持久写入是否有权提交。

## 容量边界

5000 个角色记录、5000 个同时在线连接和 5000 个在线或托管战斗实例是不同的负载。当前开发实例上限为 128 条游戏 WebSocket，角色房间共 8 个分片且每片 256 间。到达上限会限制接入。离线托管计量目前每累计一秒提交一次结算，持续托管的事务量需要随实际混合负载测量。

架构方案 §19.1 的初始单运行服目标为 1000、2000、3000 个在线或托管活跃角色逐级验证。5000 活跃角色还需要独立游戏和数据库环境的混合负载、尾延迟及长稳证据。

## 验收

- 隔离真实 MongoDB 随机数据库中，仅对测试游戏节点的控制连接截去一次已写入的续租回复。真实驱动触发两秒读取超时，约 2.26 秒恢复，节点仍持有原 owner 和 epoch。未确认期间的资产结算可核对，重查不重复执行，换代后的旧实例也不能再续租。确定性时钟测试覆盖持续失败、迟到的成功回包及明确失权。
- 另起独立 MongoDB 8.0.34 进程，8 个写线程逐条等待多数确认与 journal 落盘。5000 条模拟角色记录全部写入，耗时 2.950 秒，P99 为 8.983 毫秒，最慢 28.740 毫秒。并行续租样本 12 次均成功。该短测覆盖记录写入，在线与托管战斗容量另行验收。
- Go 全包通过，真实数据库的入场、健康重连、地图往返与所有权围栏回归通过。试玩空闲时重启服务端启用修复，三节点健康，专属 MongoDB 沿用原运行实例。
