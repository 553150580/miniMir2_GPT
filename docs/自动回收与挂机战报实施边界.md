# 自动回收与挂机战报实施边界

日期：2026-10-29。基线提交99ce2857；本阶段已通过限定开发验收，完整P0仍未完成。实际检查和边界见《自动回收与挂机战报阶段验收.json》。

依据《最终策划案》4.2的分解与自动回收、背包满规则，及4.12的托管逐事件结算要求，实现免费玩家可设置的自动回收、装备锁定和实际战报。在线与托管走相同角色owner事务，不能在客户端按时间估算收益。

## 设置与保护

策略随角色永久保存，旧角色缺省关闭、策略修订0。玩家选择品质、装备需求等级上限（0表示不限）、按物品配置ID保护的类型，以及绑定/非绑定保护。打开设置页只创建草稿，不暗中提交；保存使用永久操作ID、原策略修订、角色修订和规则版本。成功只推进一次EconomicSeq、Role.Revision及策略修订，不占SourceSeq。

穿戴、锁定、资产占用及未确认培养结果是不可关闭的强保护。按背包实例处理并交叉排除穿戴实例；手动分解同样不能绕过强保护。锁定按原实例ID和版本原子修改；不创建第二套本地锁。当前尚无装备培养待选业务，预留的规范占用状态用于服务端保护，不能把本阶段写成已经实现洗炼或仓库。

“保存设置”只影响未来；“应用到现有背包”另行明确确认，与策略修改在同一资产事务提交。满包已经停止拾取时，此操作可释放空间；只有真实有空格才能解除PickupStopped，自动战斗仍由玩家主动开启。

## 分解配置边界

玩法数值继续只维护outputs/development-prep-20261026/两本唯一Excel。本轮从既有game_equipment投影需求等级，不由物品名或角色等级推断；缺少需求等级或回收定义时保留装备并给出原因。

现有木剑218的50金币、布衣193的400金币仅为原profile开发事务夹具，不是正式分解价值。显式equipment_recycling.mode=development_gold_only、outputs=[]只声明当前开发子集；继续使用原Item.RecycleGold，不复制第二价格表。game_recycle_values正式金币分布、损坏副产物、洗炼石及祝福油仍待核验，不把null当成零或声称正式分解表已发布。本轮不新增持久损耗或验收损坏装备回收。

## 每次结算

原击杀事实、随机结果及物品实例ID保持冻结。每个事件只使用一次SourceSeq，回收并入Store.Settle的原事务：先按已提交策略处理可回收背包装备，再处理本次掉落；命中新装备可直接回收，最后才判断背包容量。仍无空间时明确放弃新掉落并记录原因，沿现有托管停止机制处理。不能为回收另发异步来源任务、先发收益后补存或在重试时重抽。

每件装备的回收产物继承该原实例的Bound，不按回收时特权重判；回收金币不受托管卡直接击杀收益加成。EXP、保底游标、回收产物、托管扣时、丢弃记录、战报和审计同事务提交。未知提交保留原操作/来源身份并查原结果，旧角色或旧票回执不得改变当前角色面板。

战报分列实际回收数量、非绑/绑定回收金币、丢弃数量和最后原因。total_drop_count计原怪物选中物品总数；drops最多100条是已入包样本，须明确显示，不当作全量。统计只属于原HostingSession，不把在线应用策略或手动回收写入旧托管战报，不从背包减少或钱包差额推算收益。

在线结果使用只读40018 EquipmentRecycleResult，以永久RoleKey、角色修订和原SourceSeq或16字节op_id识别原提交；trigger区分逐事件自动、明确应用背包和手动分解。客户端按当前角色与单调提交水位去重，历史重入不补播旧提示。通知失败不回滚资产，不生成第二次回收。
